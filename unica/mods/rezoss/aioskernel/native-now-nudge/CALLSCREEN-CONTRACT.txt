control the phone. Cloud/Gemini schemas were deliberately excluded.

Implementation
--------------
CallScreeningContract adapts recognized Samsung conversation/schema/language
into Qwen instructions. Conversation is quoted as untrusted data. The dedicated
output parser rejects extra, missing, duplicate, nested, nonstring fields,
trailing content, empty answers and control tokens. Escaped quotes/backslashes
are rejected because InCallUI removes backslashes before reparsing JSON.
No deterministic intent classifier or invented completion state was added.
TextBackend accepts call_screening_response after actual model validation,
snapshots the selected UID profile into each task, keeps existing Binder
callbacks/IDs/cancellation/UID checks, bypasses ReplyText cleanup for JSON,
and limits screening generation to 128 tokens within the 1024-token context.
The screening deadline is nine seconds from submission, including queue/lock,
model preparation, tokenization and generation. An independent timer also expires queued tasks and stops their tokenizer/runner.
Late/invalid output follows
the existing failure callback. This does not prove cold model startup can
meet Samsung's deadline; actual warm-up and response latency need device proof.
Existing contextual_reply/smart_reply behavior and Samsung filtering remain.

2026-10-29 response/timeout correction (v4 candidate)
-------------------------------------------------
Live test confirmed initial greeting and caller transcription on Wi-Fi/VoIP,
then a V73 inference timeout and accepted literal answer=answer. Samsung's
NO_REQUEST_TIME_OUT path repeated the accepted answer. V6 cellular proxy-TX
activation was not observed in that call; audio changes remain independent.

CallScreeningContract now rejects label-valued fields, punctuation/symbol-only
fields, placeholder spoken answers (including repeated answer/response), and
oversized fields. Purpose=nothing is still allowed as caller data; a spoken
answer consisting solely of nothing is rejected. No replacement facts or
scripted success are generated. Compact multilingual instructions request a
single spoken sentence of at most eight words. Generation cap is 48 instead
of 128 tokens, to reduce excessive work; the full JSON must still validate.

ScreeningDeadline atomically owns one terminal result and checks success
against nine seconds from submission even if the timer is delayed. Queue,
import, tokenize and generation time remain included. Explicit cancellation
and client death remove queued work. Task cleanup destroys its native process.
Timing logs report tokenization/request age without dumping conversation text.
The native runtime still loads per request. This is not persistent warm-up
and does not prove that every cold inference fits Samsung's response window.
Observed old runner logs include 27-30 generated tokens taking 9.6-11.5seconds.
Do not lengthen Samsung's timeout or return placeholders as a workaround.
