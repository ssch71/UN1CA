Samsung Memory ROM integration and three-finger gestures
2026-11-09 / dm3q only

Source placement
Everything belongs to unica/mods/rezoss/memory. There is no standalone mods/memory
module. The parent rezoss/customize.sh sources memory/integrate.sh after its base
overlays. Backups of the previous module and parent script are retained locally
in out/archived/memory-gesture-port-20261109/.

Gesture behavior
Three fingers swipe DOWN  -> Memory screen capture
Three fingers swipe RIGHT -> Memory voice capture
Three fingers swipe LEFT  -> Memory camera capture
Swipe up, taps, pinches, other finger counts and continuous repeats do not launch
Memory. A gesture that exceeds three fingers or is cancelled cannot launch a
Memory action. Only one launch is allowed per input stream.

Memory's existing memory_three_finger_gesture secure setting enables all three
mappings. It is off when absent; the integration does not set it automatically.
Memory normally sets it during completed onboarding, or from its gesture switch.
The original Memory switch description mentions screen capture only; the signed
APK has not been modified to describe the additional left/right mappings.

Home Up retains priority whenever the launcher's effective multi-finger master
state is enabled OR home_up_multi_finger_gesture_enabled is 1. Disable Home Up's
multi-finger gestures to use Memory's path. The bridge observes both secure keys,
so changes do not require reboot or launcher restart. It never writes Home Up
configuration or rewrites saved gesture actions. An already-started Memory input
stream cannot fall through into stale Home Up actions when settings change.

Implementation
The existing One UI Home MultiFingerGestureDetector recognizes the swipe. Four
method-local hooks in two classes add the independent Memory enable/dispatch
path, without changing original .locals counts or removing original controls:
  GestureInputHandler.isMultiFingerGestureEnabled
  MultiFingerGestureInputHandler.hasAnyMultiFingerGestureEnabled
  MultiFingerGestureInputHandler.onMotionEvent
  MultiFingerGestureInputHandler.handleMultiFingerGestureEvent
The detector itself is unchanged. Existing dominant-axis/swipe thresholds,
SystemGestureUseCase gating, navigation-region rejection, immersive/keypad rules
and excluded-app checks remain. There is an additional unlocked-user and unlocked
keyguard check before dispatch and again before the posted activity launch.
Recognized actions use the existing input monitor to cancel the underlying touch
stream, matching the launcher's pilferPointers mechanism. No new global monitor,
background app service, launcher icon, companion APK or Home Up patch is added.

Screen -> exported feature.capture.ScreenCaptureViewerActivity.
Voice -> exported feature.main.MainActivity with action ADD_MEMORY_VOICE.
Camera -> exported feature.main.MainActivity with action ADD_MEMORY_CAMERA.
The latter two are Memory's own declared launcher shortcut actions. Voice uses
that path because ExternalVoiceCaptureActivity requires the custom signature/
privileged permission EXTERNAL_VOICE_CAPTURE; no permission bypass is added.

Supported scope
Main display, full gesture navigation (NaviMode.NO_BUTTON). The existing outer
navigation/display and safety gates are preserved. Three-button navigation is
not supported by this patch. Read-only live inspection showed SystemUI bound to
One UI Home's TouchInteractionService while Nova was default, with the swipe-up
input monitor active. That establishes the lifecycle candidate, not working
patched capture. Home Up uninstall behavior remains a device-test requirement.

prepare-launcher.sh decodes only code into a new /tmp directory, strictly dry-runs
and applies patches/0001-Add-independent-Memory-capture-gestures.patch with fuzz=0,
assembles classes3.dex and new classes6.dex, and retains the original APK container.
Only classes3.dex is replaced and classes6.dex added; AndroidManifest.xml,
resources.arsc, all resource names, assets, native libraries and other DEX remain
byte-for-byte unchanged. It signs with the build's normal aosp/unica platform key
and verifies signature, alignment and ZIP integrity before staging. External
launcher oat/.prof/.bprof files are removed through DELETE_FROM_WORK_DIR because
they describe the old DEX. No common multi-device build scripts were changed.

existing gesture DEX's method table. Compile-only launcher stubs are not packaged.

Remaining requirements and limits
At initial offline validation, no full ROM build, phone installation, flash,
reboot or live gesture test had been performed. Subsequent device results are
recorded below. Longer-term boot/launcher stability, actual
screen/voice/camera saving, rotation, Nova, Home Up on/off/uninstalled and permission
prompts still require device validation. Protected-screen restrictions are not
bypassed. The original native Memory-specific gesture handler remains unidentified.
This integration intentionally supplies a launcher path instead.

The earlier dependency investigation remains applicable: the default Memory AI
model uses SCS_SPAC_GEMMA_4_31B_MEMORY, but the inspected phone exposes no matching
IntelliVoice SpacClientService. Moneta ActiveMemoryProvider and Galaxy Agent were
also absent. No AI backend port was attempted here. Three optional native names
(libLttEngine_RR.so, libsdk-jni.vexfwk.samsung.so, libapex_jni.media.samsung.so) are
absent from target and donor; inspected code uses available newer alternatives.
No additional native-library copy is currently justified. Detailed original
analysis is retained in out/archived/memory-1.0.00.46-investigation/REPORT.txt.

Rollback
Place a disable marker at unica/mods/rezoss/memory/disable before a clean ROM build
to skip both Memory packaging and launcher gestures. This does not uninstall a
user-installed Memory APK or change any phone setting. Removing that marker
restores integration. Do not mix the patched launcher with a different baseline.

Volume Up + Side voice capture (2026-11-10)
Implemented in sidekey/0001-Add-Memory-volume-up-side-key.patch, applied by
integrate.sh through the existing shared services.jar patch workflow. Memory.apk
and the three-finger launcher patch are unchanged by this addition.

Conflict findings from the exact dm3q framework:
- KeyGestureController constructs rule class ID 5 for keys 24 + 26 (Volume Up +
  Power). InputRune.PWM_KEY_COMBINATION_VOLUP_POWER selects gesture type 1001.
- Its LocalKeyGestureEventHandler routes type 1001 to Samsung Accessibility
  Direct access. The native rule already checks SecureLockDeviceService.
- AccessibilityDirectAccessController uses the current user's secure setting
  accessibility_direct_access_target_service. Any nonempty assignment therefore
  takes priority over Memory; the original branch runs without modification.
  When unassigned, Memory replaces the default Direct access chooser behavior
  only while the eligibility checks below pass.
- Volume Up + Volume Down is a separate accessibility rule and is untouched.
  Volume Down + Side screenshot/power-menu handling, single/double/long Side
  presses, ringer gestures and non-Samsung gesture types are untouched.
- PWM_DEVICE_SHUTDOWN_VOLUP_POWER_CHN reserves this combination for regional
  shutdown behavior; Memory declines the entire chord when that flag is true.
- Read-only connected-phone checks: Direct access target null, region FRANCE.
  No permission, setting, package or firmware changes were made for this work.

Behavior and activation:
Press Volume Up + Side together while the screen is on and the phone is
unlocked. The native detector retains its existing 150 ms chord matching window
and key consumption. Memory opens MainActivity with ADD_MEMORY_VOICE, the same
voice entry point verified by the earlier swipe-right runtime test. Recording,
microphone permission prompts and AI processing remain Memory's responsibility.

The shortcut defaults on when this ROM integration is present. A separate
per-user secure setting, memory_volume_up_side_key, disables it when set to 0;
absence defaults to 1. It does not depend on memory_three_finger_gesture or
Home Up, and no settings are written during boot/build. No new settings UI was
added. To disable just this shortcut (manual command, not run by this session):
  /mnt/c/platform-tools/adb.exe shell settings --user 0 put secure memory_volume_up_side_key 0
Set it to 1 to enable again. With the shortcut off, the stock Direct access
branch remains available. The existing memory/disable marker skips the complete
integration in a clean ROM build, including this framework patch.

Eligibility also requires provisioning and user setup complete, current user
unlocked, no keyguard/device lock, no SecureLockDeviceService restriction, and
an enabled/exported Memory voice entry point installed for the current user.
The queued launch rechecks eligibility and current user before starting it.
Native START owns a Memory chord and launches once; duplicate START callbacks
and the native cancelled-COMPLETE cleanup never launch a second capture. Stock
chords cannot be stolen if settings change while the buttons are held.

Framework patch safety and validation:
- Only the type-1001 branch of LocalKeyGestureEventHandler is hooked. Existing
  .locals 21, labels, exception regions and original instructions are retained.
- Five exact native detector/rule/handler files are guarded by targets.sha256.
  Stock firmware, compiled working JAR decode and existing shared patched
  decode match those guards. A mismatch or prior application stops integration.
- No other unica patch touches these classes; all other services.jar mods use
  the normal shared decode and remain composable. A zero-fuzz dry-run is required
  before APPLY_PATCH. Helper classes are added to classes2.dex; compile-only
  Android/server stubs are excluded from the generated patch.
- 1,212 ownership/repeat/cancellation policy checks pass, together with the
  existing 41 three-finger checks and original-container packaging checks.
- Exact temporary zero-fuzz apply, full project Apktool services.jar rebuild
  and ZIP integrity checks pass. Real-helper integration staging passes for
  both existing Memory packaging and the framework patch, with disabled,
  incompatible-target and previously modified-policy rejection checks.
